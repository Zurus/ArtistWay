# Запуск разработки — инструкция

Документ отвечает на вопрос: «что нужно сделать, чтобы перейти от `docs/`
к работающему приложению». Все промпты для разработчика (нейросети) —
в `docs/prompts.md`, отправляются строго по одному и по порядку.

## 1. Одноразовая подготовка (до первого промпта)

### 1.1. JDK 17

Собирать Android-проект нужен JDK 17 (на машине сейчас только Java 8 —
ее недостаточно).

- Установить JDK 17 (например, Eclipse Temurin): https://adoptium.net/temurin/releases/?version=17
- Задать переменную окружения `JAVA_HOME` на папку JDK
  и добавить `%JAVA_HOME%\bin` в `PATH`.
- Проверить в **новом** терминале: `java -version` → `openjdk 17.x`.
- У Android Studio есть встроенный JBR, но из командной строки он не
  виден — отдельный JDK всё равно нужен.

### 1.2. Android Studio + Android SDK

- Установить Android Studio (stable): https://developer.android.com/studio
- При первом запуске через SDK Manager установить:
  - SDK Platform `android-35` (API 35);
  - SDK Build-Tools (последние);
  - Platform-Tools.
- Путь SDK по умолчанию: `C:\Users\<user>\AppData\Local\Android\Sdk`.
  После этапа 1 путь пишется в `local.properties` (`sdk.dir=...`) —
  этот файл в git не попадает (см. `.gitignore`).
- Для запуска приложения (нужно с этапа 4): эмулятор или физическое
  устройство с USB-отладкой. Этапы 1–3 эмулятор не требуют —
  достаточно `assembleDebug` и unit-тестов.

### 1.3. Gradle — ставить не нужно

Проект собирается **Gradle Wrapper** (`gradlew` / `gradlew.bat`), который
создаётся на этапе 1 (промпт 6). Версия Gradle фиксируется в
`gradle/wrapper/gradle-wrapper.properties` (Gradle 8.x); при первом
запуске `./gradlew` дистрибутив скачается автоматически
(нужен доступ в интернет).

Системный Gradle 3.5 на этой машине (`C:\Program Files\gradle-3.5`)
не используется вовсе — обновлять и переустанавливать его не нужно.

### 1.4. TMDB API-ключ

1. Регистрация: https://www.themoviedb.org/
2. Аватар → **Settings → API** → **Create API key** → тип **Basic (v3 auth)**.
3. Ключ положить в `local.properties` в корне проекта (файл создаётся
   на этапе 1 или ранее вручную):

   ```text
   sdk.dir=C\:\\Users\\<user>\\AppData\\Local\\Android\\Sdk
   TMDB_API_KEY=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
   ```

4. В коде ключ читается только через `BuildConfig.TMDB_API_KEY`
   (требование зафиксировано в промпте 7) — не вставлять ключ
   в коммитимые файлы.
5. Лимиты TMDB: 100 запросов / 10 секунд на IP. Для MVP этого достаточно:
   превышения обрабатываются `RateLimitInterceptor` (см. ниже, «Нюансы»).

### 1.5. Репозиторий

- `.gitignore` создан: игнорируются `local.properties`, `.idea/`,
  `build/`, `.gradle/` — ключ и артефакты сборки в git не попадут.
- Перед первым кодовым промптом текущее состояние `docs/`
  закоммитить (промпт 0 в таблице §3).

## 3. Порядок работы

Промпты 6–12 в `docs/prompts.md` покрывают все 6 этапов `docs/05_roadmap.md`.
Отправлять **по одному за раз**. После каждого — проверка и коммит.

| # | Что отправить | Результат | Как проверить | Коммит (если одобряете) |
|---|---|---|---|---|
| 0 | «Закоммить текущее состояние доков» | чистый git-статус | `git status` | `[docs] [задача] Согласовать доки перед разработкой` |
| 1 | промпт 6 | каркас проекта | `./gradlew assembleDebug`; приложение запускается (пустой экран) | `[код] [задача] Этап 1 roadmap: фундамент и контракты` |
| 2 | промпт 7 | фильмография актёра | unit-тест: повторный вызов без сетевого запроса | `[код] [задача] Этап 2 roadmap: срез data layer (фильмография)` |
| 3 | промпт 8 | data layer целиком | критерии приёмки пункта 2 roadmap | `[код] [задача] Этап 2 roadmap: завершение data layer` |
| 4 | промпт 9 | домен + UseCase | `./gradlew test`, покрытие `domain/util` ≥ 80% | `[код] [задача] Этап 3 roadmap: домен и UseCase` |
| 5 | промпт 10 | MVP UI, 5 экранов | вручную: полная партия на реальных данных TMDB | `[код] [задача] Этап 4 roadmap: MVP игрового цикла` |
| 6 | промпт 11 | edge cases | ручной чек-лист `docs/01_concept.md` §6 | `[код] [задача] Этап 5 roadmap: edge cases` |
| 7 | промпт 12 | полировка/релиз | `./gradlew assembleRelease lint detekt test`; QA-чеклист | `[код] [задача] Этап 6 roadmap: полировка и релиз` |

### Правила

- Пропускать промпты нельзя: каждый следующий ссылается
  на файлы предыдущих.
- Результат не соответствует критериям приёмки — не переходить дальше,
  отправить уточнение:
  «Исправь: <что не так>. Критерий — пункт N `docs/05_roadmap.md`, критерии приёмки».
- Коммиты и push — только после явного вашего одобрения.
- Формат сообщений коммитов (проверяется хуком):
  `[команда] [бик/дефект/задача] сообщение`.
- Статусы этапов в таблице обзора `docs/prompts.md` обновлять по мере
  выполнения.

## 4. Команды сборки и проверки

```bash
./gradlew assembleDebug      # debug-сборка
./gradlew test               # unit-тесты (domain, data)
./gradlew lint detekt        # статический анализ
./gradlew connectedCheck     # instrumented-тесты (нужно устройство/эмулятор)
```

В Windows CMD вместо `./gradlew` — `gradlew.bat`.

## 5. Известные нюансы

- **Лимит TMDB.** 100 запросов / 10 с на IP. Бюджет генерации
  (`maxRequests` 200–400) может быть растянут из-за `429` + повторов;
  реальные значения `Budget`/`PairGenConfig` выверяются на этапе 6
  (критерий: 10 генераций укладываются в бюджет, замер — в
  `docs/QA_CHECKLIST.md`).
- **Время генерации пары.** Ожидание — до ~8–10 с в лучшем случае,
  дольше — при rate limit. UI показывает прогресс генерации
  (`GameSetup`), это учтено в roadmap (этап 4).
- **Process death.** Активная сессия восстанавливается из Room
  (критерий этапа 4 roadmap).

## 6. После MVP: как продолжать разработку (локализация, поиск и т.п.)

`docs/` описывает **MVP**; что отложено — в конце `docs/05_roadmap.md`
(«Что не входит в MVP»). Добавляя функцию, не отправляйте голый промпт
«добавь локализацию» — сначала спека, потом промпт. Цикл тот же,
что и при разработке MVP:

### 6.1. Порядок

1. **Обновите/дополните документацию** (источник истины — доки, код следует за ними):
   - меняется поведение MVP — правьте затронутые доки:
     напр. локализация — `docs/03_data_layer.md` §3 (локаль `en-US` → `ru`,
     `originalTitle` становится fallback'ом, а не основным значением);
   - новая функция — короткий новый документ в `docs/`
     со следующим номером (напр., `docs/07_localization.md`):
     что это, UX, данные, edge cases, что меняется в существующих доках.
2. **Добавьте этап в `docs/05_roadmap.md`** (или новый roadmap на релиз):
   цель, список файлов, критерии приёмки, оценка — как в этапах 1–6.
3. **Добавьте промпт в `docs/prompts.md`** со следующим номером (13+)
   в том же формате: «Контекст» (какие доки читать), «Задача»,
   «Требования», «Результат», статус «не выполнен». Обновите таблицу обзора.
4. **Отправляйте промпты по одному**, проверяйте критерии приёмки,
   коммитьте по этапам — правила из §3.

### 6.2. Пример — локализация

- `docs/03_data_layer.md` §3: локаль `ru`; правило «нет `ru` →
  `originalTitle`» (механизм уже заложен: локаль — параметр
  Retrofit-интерфейсов, DTO при переключении не меняются).
- Новый документ `docs/07_localization.md`: строки интерфейса
  (`stringResource`), плюралы/даты, судьба закэшированных данных
  на `en-US` (TTL или миграция кэша).
- `docs/05_roadmap.md`: этап «Локализация» — файлы, критерии, оценка.
- `docs/prompts.md`: промпт 13 «Локализация», статус «не выполнен».
- Затем — отправляете промпт 13.

### 6.3. Правила

- Не ломать инварианты MVP: переход только через `cast`, пара — только
  при существовании пути ≤ `maxSteps`, тупик — валидное состояние
  (см. конец `docs/05_roadmap.md`).
- После MVP пометьте релиз тегом (напр., `git tag v0.1.0-mvp`),
  чтобы новые функции начинались от известного состояния.
- Не смешивайте: один промпт — один этап одной функции, и доки
  к ней закоммичены до отправки промпта.
