# Цикл отладки: реальный телефон + реальный TMDB

MVP проверен на JVM (Robolectric/MockWebServer). Первый запуск релизного APK
на реальном телефоне с реальным TMDB выявил проблему: игра не стартует.
Этот файл — цикл отладки: данные → гипотеза → промты **по одному за раз**.

## Файлы в `debugging/`

| `start_screen.PNG` / `start_screen.txt` | экран Home + logcat на старте приложения |
| `limit.PNG` / `limit.txt` | экран ошибки + logcat до ошибки |

Папка зашита в `.gitignore` (в логах TMDB-ключ входит в URL) — **не коммитить**.

## Факты, уже читаемые из данных

1. **TMDB с телефона достижим**: все ответы в логах `200` (VPN сейчас работает).
   Блокировка — не причина.
2. **Экран ошибки — «Исчерпан бюджет вычислений. Попробуйте ещё раз.」**
   (`error_budget_exceeded`) — это `PairGenerationError.BudgetExceeded`:
   пара не сгенерирована, потому что исчерпан бюджет генерации.
3. **Гипотеза (высокая вероятность): wall-clock бюджет слишком мал.**
   `Budget.DEFAULT_MAX_WALL_CLOCK_MS = 6_000` (6 секунд), а сеть телефона
   гоняет TMDB ~0.6–1.1 с на запрос (первый `configuration` — 3.9 с).
   BFS успевает ~6–7 запросов — этого не хватает даже на первую пару.
4. `start_pool_130`: реально **107** актёров (130 — потолок, не цель;
   собрано 97 фильмов). ID целы; в двух строках-комментариях encoding-бит
   от переноса скрипта на твою машину («—генерировано», «попул¤рных») —
   на данные не влияет, парсим по числам.
5. **Рассогласование ID у RDJ**: в старом пуле `2871 (Robert Downey Jr.)`,
   в новом `3223 (Robert Downey Jr.)`. Имена в новом пуле пришли из TMDB
   (credits API), значит 3223 — надёжнее; 2871 проверить по `person/2871`.
   Возможно, один из старых 13 ID — «не тот человек».
6. Часы телефона стоят на 2026-11-25 (по логам). Сейчас не причина
   (TLS с TMDB прошёл), но риск для других сервисов — проверить.

### D1. Добиться старта: почему «Исчерпан бюджет вычислений» — диагноз + фикс

**Задача.** На основе логов в `debugging/` подтвердить (или опровергнуть)

**Контекст.** `debugging/start_screen.txt`, `debugging/limit.txt`

`docs/04_algorithms.md` §3.6 (бюджеты).

**Требования (критерии приёмки).**

- Подтвердить по логам гипотезу: wall-clock 6 с против ~1 запроса/сек →
  `BudgetExceeded` уже на первой паре.
- Минимальный фикс (варианты — решение в диалоге):
  - поднять `maxWallClockMs` под реальную сеть (60–120 с), или
  - адаптивный бюджет: после первых 2–3 запросов замерить среднюю

  есть); ANR исключён (генерация — background-корутина).
- Алгоритмы BFS/`PairGenerator` **не** менять (минимальное вмешательство).
- Тесты: `Budget` (новые лимиты/адаптация), существующие 177+ зелёные,
  `detekt`/`lint` зелёные.

**Результат.** На телефоне: «Начать игру» → пара показана (загрузка до
~60 с допустима), игровая сессия работает. Если ошибка повторится —
новый лог `debugging/step2_start.txt` и следующая итерация D1.

> Статус: ✅ выполнено (коммит `93bb4b0`, pushed). Причина подтверждена
> (wall-clock 6 c против ~1 запроса/с). Фикс: двухуровневый бюджет —
> внешний `@GenerationBudget` (500 запросов / 20k узлов / 120 c) +

### D5. Дешёвый онлайн-поиск d=2 («пересечение составов») + глубина на старте

**Задача.** Сократить 5–10× стоимость онлайн-подбора пары глубины 2:
для d=2 — пересечение множеств ко-актёров вместо обобщённого BFS
(«взрыв» среднего слоя убирается); на стартовом экране — выбор глубины
пары 2/3/4.

**Контекст.** `GamePairRepositoryImpl.generatePair` (D1: per-pair/внешний
бюджеты, skip дорогих пар), `domain/util/Bfs.kt` (**не менять**),
`PairGenConfig` (minSteps=2, maxSteps=6), `GameSetupScreen`/
`GameSetupViewModel`, `GamePair` (start, target, shortestPath —
используется в детекте тупиков).

**Требования (критерии приёмки).**

- Новый поиск d=2 (data-слой): для пары (A, B) — фильмографии A и B +
  составы их фильмов (через существующие репозитории/GenCache; реальные
  запросы учитываются в бюджетах D1), пересечение ко-актёров в памяти;
  общий X → `GamePair` с путём `[fA, X, fB]` (2 перехода). **fA ≠ fB**
  обязательно: иначе d=1-пара (A и B делят один фильм) замаскируется
  под d=2 — если общий ко-актёр только в общих фильмах, пара
  отбрасывается. Стоимость пары ≈ N(A)+N(B)+2 запросов; данные об A
  переиспользуются для других пар через кэш.
- `generatePair(seed, depth)`, depth ∈ {2,3,4}: d=2 — пересечение;
  d=3–4 — существующий целевой BFS с maxSteps=depth (без изменений).
- Стартовый экран: переключатель 2/3/4, default **2**, выбор
  сохраняется (SharedPreferences); для 3–4 — честная пометка «на
  медленном соединении — несколько минут»; текст спиннера — по глубине.
- Экран правил: строка про глубину пары.
- Бюджеты D1 не меняются (per-pair 30с/1500 узлов, внешний
  120с/500 запросов) — они же охраняют пересечение.
- Тесты: пересечение (нашёл путь / пар без общего ко-актёра →
  следующая / повторное использование данных A: вторая пара с тем же A
  не запрашивает его фильмографию заново); **d=1-пара не маскируется
  под d=2** (fA≠fB — регресс-тест); ViewModel: default 2, смена, передача
  в use case, сохранение; существующие 182+ зелёные, detekt/lint, release.
- Доки: `docs/04_algorithms.md` §5.4 — приписка D5 (пересечение, fA≠fB,
  глубина).

**Результат.** На телефоне (медленный канал): глубина 2 → пара за ~1–5
минут на холодном старте (каждый повтор быстрее — Room теплеет), вместо
15+ повторов; глубины 3–4 — как раньше, с пометкой.

> Статус: ✅ код завершён (unit-тесты, detekt, lint, release — зелёные).
> d=2 — `DepthTwoPairSearch` (пересечение ко-актёрных множеств,
> fA≠fB — d=1-пара не маскируется под d=2); d=3–4 — целевой BFS
> (`maxSteps = depth`). Стартовый экран: выбор 2/3/4 (SharedPreferences,
> default 2), пометка «несколько минут» для 3–4; экран правил — строка
> про глубину. Телефонный смоук — D9.

### D8. Паттерн Стратегия: выбор пары как сменный источник

> Это рефакторинг момента выбора пары (D1-бюджет, D5 онлайн d=2,
> D7 банк). Если D5 и D7 ещё не сделаны — сначала выполни их по
> порядку, затем этот промт. Цель: код знает «откуда взять пару»
> только через один интерфейс, а «откуда именно» решает
> `local.properties`. Подробное описание четырёх источников —
> `docs/pair_sources.md`.

**Задача.** Ввести паттерн Стратегия для старта игры: интерфейс
`PairSource` в домене, реализации в data-слое, выбор через
`BuildConfig.PAIR_SOURCE`.

**Стратегии (источники пар):**

1. `online` — уже существующие алгоритмы: `GamePairRepositoryImpl`
   (HARDCODED_PAIRS + целевой BFS, двухуровневый бюджет D1) + дешёвый
   поиск d=2 (D5, если сделан). Адаптер вокруг существующего кода —
   без переписывания.
2. `bank` — заранее сгенерированный банк `pairs_bank_v1.json`
   (D4/D7): 0 запросов. Строго: если запрашенная глубина в банке не
   покрыта → `NoValidPair`, без fallback.
3. `remote` — запрос к микросервису пар (P3, post-mvp): пока — заглушка:
   интерфейс и место в DI на месте, в рантайме — понятная
   `PairGenerationError` («микросервис пар ещё не подключён»); контракт
   эндпоинта — в P3.
4. `auto` (по умолчанию) — банк → онлайн: если запрашенная глубина
   покрыта банком — банк (0 запросов), иначе — онлайн, без ошибки и без
   переключателя в UI (семантика D7 «приоритет с fallback»).

**Другие способы в коде.** Известный второй «способ» — `PairGenerator`
(domain/util, пуловой BFS, основа P4): он не должен обходить
`PairSource` в стартовом пути — либо обернуть его в стратегию, либо
явно зафиксировать в доках как P4 (вне MVP-старта). Если аудит
покажет другие точки выбора пары — привести к `PairSource` или
задокументировать.

**Выбор.** `local.properties` → `BuildConfig.PAIR_SOURCE`
(строка `auto` | `online` | `bank` | `remote`, по умолчанию `auto`) —
тот же механизм, что `tmdb.logging` и TMDB-ключ. Если D7 ввёл
булевый `pairBank.enabled` — заменить на этот (`auto` ≡ true,
`online` ≡ false). Неизвестное значение → `auto` + предупреждение в
логе. Выбор на время сборки (rebuild), UI-переключателя в MVP нет.

**Архитектура (Clean).**

- Домен: `interface PairSource { suspend fun pick(config: PairGenConfig, seed: Long?): Result<GamePair, PairGenerationError> }` —
  глубина/лимиты приходят в `PairGenConfig` (банк выбирает по глубине,
  remote уйдёт в запрос). Модель ошибок не меняется —
  `PairGenerationError`.
- Data: `OnlinePairSource` (адаптер вокруг логики
  `GamePairRepositoryImpl`, включая бюджеты D1 и гидратацию актёров
  `toDomain`), `BankPairSource` (лоадер D7 + `getActor`),
  `RemotePairSource` (заглушка), `AutoPairSource` (банк → онлайн).
- DI: Hilt `@Provides pairSource()` — `when` по
  `BuildConfig.PAIR_SOURCE`.
- `StartGameUseCase` (и всё, что выше: VM, UI) знает только
  `PairSource`.
- Без дублирования логики: BFS, бюджеты, лоадер банка — только
  оборачиваются.

**Требования (критерии приёмки).**

- `PAIR_SOURCE` в `build.gradle.kts` (default `auto`); задокументирован
  в `docs/06_getting_started.md` и README (раздел «Способ подбора пар»
  уже есть — актуализировать под реализацию).
- `auto`: глубина 2 → банк (0 запросов к TMDB — проверяется в тестах),
  глубины 3–4 → онлайн (банк MVP содержит только d=2).
- `online`: поведение равно текущему — существующие тесты зелёные без
  правок.
- `bank`: без fallback; `remote`: понятная ошибка, без краша.
- Unit-тесты каждой стратегии (фейковые репозитории/лоадер), DI-выбор
  (4 значения + неизвестное → `auto`), `StartGameUseCase` с каждым
  источником.
- Все тесты зелёные, detekt, lint.
- Доки: `docs/02_architecture.md` (раздел «Выбор пары: стратегии»),
  `docs/04_algorithms.md` (цепочка выбора по `PAIR_SOURCE`),
  `docs/06_getting_started.md` (таблица параметров local.properties),
  `docs/pair_sources.md` (актуализировать под код).

**Результат.** «Откуда брать пару» — одна строка в `local.properties`
(rebuild); микросервис (P3) подключается как новая стратегия без
касания игрового потока; дефолт `auto` = поведение MVP после D7.

> Статус: ✅ код завершён (unit-тесты, detekt, lint, release — зелёные).
> Домен: `domain/repository/PairSource.pick(config, seed)`. Data:
> `data/pairsource/` — `OnlinePairSource` (адаптер над
> `GamePairRepositoryImpl`: бюджеты D1, d=2-поиск D5, toDomain),
> `BankPairSource` (строго: непокрытая глубина → `NoValidPair`, без

> `StartGameUseCase` знает только `PairSource` (конфиг точной глубины +
> seed). Тесты: каждая стратегия, DI-выбор (4 значения + unknown),
