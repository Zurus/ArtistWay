# Способы получения пары («КиноНить»)

На старте игры приложение должно выдать пару актёров
(стартовый → целевой), между которыми **гарантированно** существует
цепочка «актёр → фильм → актёр» нужной глубины (глубину игрок
выбирает на стартовом экране, 2–4).

«Откуда взять пару» — сменная стратегия (паттерн Strategy,
`docs/debugging.md` D8): интерфейс `PairSource` в домене, реализации
в data-слое, выбор — одна строка в `local.properties`
(`PAIR_SOURCE`). Игрок и остальной игровой поток этого не видят.

Этот документ описывает четыре источника пар подробно и независимо
от кода; реализации — по мере выполнения D5–D8.

## Общий контракт (что отдаёт любой источник)

- **Пара** — `GamePair`: стартовый актёр, целевой актёр, кратчайший
  путь (цепочка) между ними, seed. По кратчайшему пути игрок
  гарантированно может пройти за `длина(пути)` шагов.
- **Глубина** — пара должна быть ровно/не глубле запрошенной
  (лимиты приходят в `PairGenConfig`: `minSteps..maxSteps`).
- **Пары d=1 (общий фильм) — не выдаются**: тривиальные, игра их
  отбраковывает как скучные.
- **Ошибки — валидные состояния, а не краши:**
  - `NoValidPair` — пары нет (источник не покрывает глубину, пул пуст);
  - `BudgetExceeded` — бюджет онлайн-поиска исчерпан («попробовать
    ещё раз»);
  - `DataError` — сеть/база: понятный текст + «Повторить».

Все источники берут актёров из **пула 117** (`GamePairRepositoryImpl.PAIR_ACTORS`).

## 1. `online` — алгоритмы, которые уже есть (BFS по TMDB)

**Как работает** (текущая реализация, закреплена D1):

1. Все 13 572 упорядоченные пары пула перемешиваются по seed.
2. Каждую пару проверяет **целевой BFS** от стартового актёра к
   целевому по графу «актёр ↔ фильм»: актёры/фильмы подгружаются с
   TMDB (Room-кэш тёплый — повторно кэшированные данные почти
   бесплатны).
3. Путь найден в пределах `maxSteps`, и его длина ≥ `minSteps` →
   пара принята; цепочка берётся из BFS-дерева (гарантия
   решаемости: путь существует по построению).
4. Бюджет **двухуровневый**:
   - суммарный на генерацию: 500 запросов / 20 000 узлов / 120 с;
   - на одну пару: 1500 узлов / 30 с — «дорогая» пара пропускается,
     берётся следующая (генерация не ломается).

**Стоимость.** Зависит от канала. Реальный канал телефона ~1 запрос/с:
от десятков секунд до нескольких минут; тёплый Room-кэш ускоряет
следующие пары в той же сессии.

| Свойство | Значение |
|---|---|
| Запросы к TMDB на старт | десятки…тысячи |
| Время | секунды…минуты |
| Глубины | 2–4 (любая со слайдера) |
| Офлайн | не работает (нужен TMDB; кэш Room помогает частично) |

**Когда выбирать.** Глубины 3–4 (банк их пока не содержит),
независимость от банка, «свежий» граф TMDB.
**Плюсы:** любая глубина, без предварительной подготовки.
**Минусы:** медленный старт на плохом канале, расход запросов.

## 2. `bank` — заранее сгенерированный банк пар

**Как работает:**

1. Оффлайн-скрипт `tools/generate_pair_bank.py` (D4) за один прогон
   запрашивает у TMDB фильмографии 117 актёров (~117 запросов) и
   составы всех их фильмов (~7 000 запросов), строит множества
   ко-актёров и для каждой упорядоченной пары без общего фильма
   записывает один путь `[fA, X, fB]` (X — общий ко-актёр, fA — фильм
   A с X, fB — фильм B с X). Детерминированно: минимальные ID.
2. Результат — `pairs_bank_v1.json` (~0.5–1.5 МБ): только ID и имена,
   **без API-ключа** → файл коммитится в `assets/`.
3. На старте приложение выбирает случайную пару нужной глубины из
   банка — **0 сетевых запросов, мгновенно**.

**Стоимость.** В рантайме — 0 запросов. Генерация — разовая:
~7 000 запросов ≈ 25–30 мин при лимите 50/10 c; у скрипта
on-disk-кэш (`tools/.pair_bank_cache/`), повторные прогоны почти
бесплатны.

| Свойство | Значение |
|---|---|
| Запросы к TMDB на старт | **0** |
| Время | мгновенно |
| Глубины | **2** (банк v1; d=3 — фаза 2 скрипта, долгая генерация) |
| Офлайн | **работает** (банк — ассет) |

**Строгость.** Если запрошенная глубина в банке не покрыта —
`NoValidPair`, **без перехода на онлайн** (это поведение `auto`
ниже).

**Когда выбирать.** Скорость, офлайн, «гарантированный» старт.
**Плюсы:** мгновенный старт, нулевой расход, не зависит от канала.
**Минусы:** глубина и пул «заморожены» до перегенерации банка
(скрипт перезапускается с ключом TMDB).

## 3. `remote` — микросервис пар (планируется, P3 post-mvp)

**Идея.** Приложение спрашивает **свой** микросервис: «дай пару
глубины N». Вся тяжёлая работа — на сервере: предвычисленные пулы,
кэши, а с P1–P3 ещё и reverse-proxy (обход блокировки TMDB, ключ
остаётся на сервере).

**Статус в MVP.** Заглушка: место в DI и интерфейс на месте (D8),
в рантайме — понятная ошибка «микросервис пар ещё не подключён».
Контракт эндпоинта зафиксируется при выполнении P3; черновик:

```
POST /api/pairs
{ "depth": 2, "poolVersion": 1 }

→ 200 {
    "start":  { "id": 2283, "name": "Stanley Tucci" },
    "target": { "id": 1245, "name": "Scarlett Johansson" },
    "path": [ ... цепочка ... ]
  }
→ 404 — пары для глубины нет
```

| Свойство | Значение |
|---|---|
| Запросы | 0 к TMDB (1 быстрый запрос к своему сервису) |
| Время | ~запрос к сервису |
| Глубины | любые (сервер предвычисляет) |
| Офлайн | не работает (нужен свой сервис) |

**Когда будет выбирать.** После P3, когда сервис поднят.
**Плюсы:** клиент лёгкий, ключа TMDB на клиенте нет, централизованные
предвычисления, обход блокировки.
**Минусы:** нужна инфраструктура, зависимость от доступности сервиса.

## 4. `auto` — банк → онлайн (по умолчанию)

Композитная стратегия: **если банк покрывает запрошенную глубину —
берём из банка (0 запросов), иначе — идём в онлайн.** Без ошибок и
без переключателя в UI: игрок просто выбирает глубину.

Поведение MVP: глубина **2** → мгновенно (банк); глубины **3–4** →
онлайн-поиск (банк v1 их не содержит).

**Почему по умолчанию.** Даёт и то, и другое: скорость на основной
глубине + покрытие всех глубин. Это же семантика, с которой D7
вводит банк («приоритет с fallback», а не «или-или»).

| Свойство | Значение |
|---|---|
| Запросы к TMDB | 0 (глубина 2) / как у `online` (3–4) |
| Глубины | 2–4 |
| Офлайн | глубина 2 работает, 3–4 — ошибка без сети |

## Связано: второй алгоритм в коде — `PairGenerator`

`domain/util/PairGenerator` — «прямой» генератор: BFS от стартового
актёра, цель выбирается из достигнутых слоёв (вариант, где целевой
актёр заранее неизвестен). Сейчас — не в стартовом пути, а основа
**P4** (профили сложности, seed-пул «top-N по popularity»). Требование
D8: не обходить `PairSource` — либо обернуть в стратегию, либо
явно зафиксировать в доках как P4.

## Переключение

Одна строка в `local.properties` + пересборка — детали в README
(раздел «Способ подбора пар»):

```properties
PAIR_SOURCE=auto    # auto | online | bank | remote
```
