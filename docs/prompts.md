# «КиноСвязи» — промпты для последовательной работы с нейросетью

Файл содержит серию промптов, из которых по порядку собираются
документация и код Android-игры «КиноСвязи».

указывающего, какие файлы модель должна прочитать, и завершается
конкретным результатом (документом или кодом).

## Как пользоваться

- Промпты отправляются **строго по одному за раз и по порядку**.
  Каждый следующий промпт ссылается на файлы, созданные предыдущими,
  поэтому пропускать этапы нельзя.
- Перед отправкой убедитесь, что файлы из блока «Контекст»
  уже существуют в проекте.
- Если результат этапа не устраивает — не переходите к следующему
  промпту, а догоните текущий уточняющим запросом.
- Статусы в таблице «Обзор этапов» обновляйте по мере выполнения.
- Промпты 6–12 покрывают все 6 этапов `docs/05_roadmap.md`
  (этап 2 — двумя срезами: 7 и 8).

## Этап 1 — Концепция (GDD lite)

**Результат:** `docs/01_concept.md`
**Статус:** выполнен

### Промпт

#### Роль
Ты — Senior Android Developer и Game Designer с опытом в казуальных играх
и работе с внешними API (особенно TMDB).

#### Контекст проекта
Мы проектируем Android-игру «КиноСвязи» (рабочее название).
Суть: игроку даётся пара (Стартовый актёр, Целевой актёр).
Задача — построить цепочку:

```text
Актёр → Фильм (где оба снимались) → Актёр → Фильм → ... → Целевой актёр
```

Пары генерируются динамически. Источник данных — TMDB API.

#### Задача ЭТАПА 1 (единственная, не выходи за её рамки)
Создай файл `docs/01_concept.md` — Game Design Document lite.
Включи следующие секции:

1. **Core Loop** — пошаговое описание одного игрового цикла.
2. **Экраны приложения** — список экранов с кратким описанием
   (что видит игрок, какие действия доступны).
3. **UX-флоу** — путь пользователя от запуска до окончания партии.
4. **Правила генерации пары** — высокоуровневые требования к паре
   (связность, длина пути, сложность). Детали алгоритма — на этапе 4.
5. **Ограничения TMDB API** — что мы знаем о лимитах,
   какие эндпоинты точно понадобятся (без детализации контрактов).
6. **Edge cases** — минимум 5 сценариев, которые могут сломать игру
   (нет пути, API недоступен, зацикливание и т.п.).

#### Формат ответа
- Markdown
- Без кода (код — на следующих этапах)
- Без архитектуры и стека (это этап 2)
- Объём: 400–700 строк, структурированно, с подзаголовками

#### Критерии качества
- Документ должен быть самодостаточным: другой разработчик,
  прочитав его, должен понять, ЧТО мы делаем, без дополнительных вопросов.
- Не придумывай механик, которых я не просил (например, мультиплеер,
  внутриигровую валюту, уровни).

### Промпт

Задача: создай `docs/04_algorithms.md`.

Опиши псевдокодом:

- Валидация хода игрока: линейная проверка цепочки
  (два соседних актёра есть в актёрском составе одного фильма,
  повторное использование актёров/фильмов запрещено,
  целевой актёр совпадает со стартовым).
- Поиск и проверка пути (BFS) между стартовым и целевым актёром —
  используется генератором для гарантии решаемости пары.
- Алгоритм генерации валидной пары (стартовый, целевой)
  с гарантией существования пути ≤ N шагов
  (ограничения: глубина, число кандидатов, бюджет запросов TMDB).
- Обработку тупиков (игрок зашёл не туда):
  отмена последнего хода, честное сообщение игроку,
  запрет бессмысленных переходов.
- Оптимизации: как не дёргать API лишний раз
  (кэширование ответов TMDB, учёт числа запросов на генерацию,
  повторное использование уже загруженных фильмов/актёров).

Без Android-кода, чистая логика.
