# docs/post_mvp_prompts.md

Промты **пост-MVP** цикла «КиноСвязи». MVP (этапы 1–6, `docs/prompts.md`)
завершён и закоммичен — этот файл запускает следующий цикл.

Очередность по ценности/риск-профилю: сначала доступность (обход блокировки
TMDB + перенос ключа на сервер), затем игровая механика (постепенное
усложнение пар, страновые ограничения, поиск актёров, локализация),
затем производительность (прогрев) и дистрибуция.

## P1. Спек reverse-proxy TMDB

**Результат:** `docs/07_reverse_proxy.md` — техническая спецификация прокси.
**Статус:** не выполнен

### Контекст

`docs/05_roadmap.md` (раздел «Что не входит в MVP»), `docs/03_data_layer.md`,
`app/src/main/java/.../data/remote/api/` (список TMDB-эндпоинтов),
`data/remote/interceptor/ApiKeyInterceptor.kt`, `data/network/NetworkConfig.kt`.

### Задача

Написать спеку reverse-proxy для TMDB. Зафиксировать дизайн-решения,
чтобы P2 реализовывался без дополнительных договорённостей.

### Требования (что должна содержать спека)

- **Цели**: (а) обход блокировки TMDB для игроков в РФ (сервер — вне РФ);
  (б) API-ключ TMDB живёт только на сервере, в APK ключа нет.
- **Стек**: Kotlin + Ktor (server), отдельный Gradle-модуль `:proxy`
  в этом репозитории; запуск — `java -jar` или Docker; деплой — VPS с
  systemd/Compose (альтернативы Fly.io/Railway — в спеке как варианты).
- **Поверхность**: прозрачная прокидка **только 8 TMDB-путьей**, которые
  использует клиент (перечислить из `Tmdb*Api`: `configuration`,
  `configuration/countries` (список стран для настроек P5),
  `movie/{id}`, `movie/{id}/credits`, `search/movie`, `search/person`,
  `person/{id}`, `person/{id}/movie_credits`); любой другой путь — `404`.
- **Ключ**: берётся из env `TMDB_API_KEY`; догоняется к query запроса
  перед прокидкой; `api_key`, присланный клиентом, **отбрасывается**.
  Отсутствие env при старте — fatal с понятным логом.
- **Rate-limit**: серверный retry на `429` с экспоненциальной задержкой
  (не более 3 повторов), затем `429` пробрасывается клиенту с
  `Retry-After` TMDB; общий бюджет ключа — лимит запросов в секунду
  по клиенту (напр., 10 rps) с ответом `429`.
- **Кэширование**: в v1 — нет (TMDB кэширует сам); зафиксировать как
  осознанный выбор + пункт «дальнейшее развитие».
- **Наблюдаемость**: `/healthz` (200 + время работы), access-лог
  (метод, путь, статус, ms) без тел ответов и без ключа в логах.
- **Безопасность**: whitelist путей, таймауты upstream (connect 5с,
  read 30с), ограничение размера тела запроса, CORS не нужен
  (клиент — наш APK).
- **Контракт клиента**: как меняется base URL (`TMDB_PROXY_URL`),
  режимы `PROXY`/`DIRECT` (dev-режим с локальным ключом — остаётся для
  разработки без сервера).
- **Тесты и приёмка**: unit-тесты на MockEngine (инжекция ключа,
  pass-through всех 8 путей, 429-retry, чужой путь → 404, нет env →
  старт падает); `./gradlew :proxy:test` и `:app:test` зелёные.
- **Дальнейшее развитие** (не в v1): кэш ответов, несколько ключей
  (пул), аутентификация клиентов, метрики Prometheus.

Критерий приёмки: спека самодостаточна — P2 отправляется без новых
вопросов по дизайну; документ согласован с `docs/03_data_layer.md`
(классификация ошибок, rate-limit) и не противоречит
`docs/02_architecture.md`.

## P2. Reverse-proxy: сервер (Ktor)

**Результат:** работающий модуль `:proxy` по `docs/07_reverse_proxy.md`.
**Статус:** не выполнен

### Контекст

`docs/07_reverse_proxy.md`, `docs/03_data_layer.md`,
`gradle/libs.versions.toml`, `settings.gradle.kts`.

### Задача

Реализовать reverse-proxy как отдельный Gradle-модуль `:proxy`:
Kotlin + Ktor (server, Netty), без зависимостей от `:app` и Android.

### Требования (критерии приёмки)

- `settings.gradle.kts` + `:proxy` (JVM 17, Kotlin 2.1.x, Ktor 3.x):
  `./gradlew :proxy:test` и `./gradlew :proxy:run` работают; fat/uber
  jar собирается одной командой (`:proxy:installShadowDist`/`jib`/
  Shadow — выбрать в спеке P1 и зафиксировать).
- Прокидываются ровно 8 путей из спеки с сохранением query-параметров
  (`language` и пр.) и статусов TMDB; любой другой путь — `404`
  c JSON `{"error":"not found"}`.
- `api_key` добавляется из env `TMDB_API_KEY`; присланный клиентом
  `api_key` отбрасывается; без env процесс не стартует (лог-строка
  с инструкцией).
- `429` от TMDB → до 3 retry с экспоненциальной задержкой (1с/2с/4с,
  ±джиттер); исчерпано → клиенту `429` с `Retry-After`.
- Лимит ~10 rps на IP (`429` при превышении) — параметр из конфигурации.
- Таймауты upstream: connect 5с, read 30с; `504` при таймауте.
- `/healthz` → `200 {"status":"ok","uptime_s":N}`; access-лог строкой
  (метод, путь, статус, ms), без ключа и тел.
- Unit-тесты (Ktor test host + MockEngine upstream): все пункты выше;
  покрытие `:proxy` main-кода ≥ 80% по строкам.
- `Dockerfile` (jre-образ, `TMDB_API_KEY` через env) + `docker-compose.yml`
  с портом 8080; README: запуск локально и на VPS (systemd-юнит примером).
- `./gradlew build detekt` на уровне корня (включая `:proxy`) — без
  ошибок; `:app:test` не деградирует.
- Detekt-конфиг распространяется на `:proxy` (общий `detekt.yml`).

## P3. Reverse-proxy: клиент

**Результат:** приложение ходит в TMDB через прокси; в release-путь
ключ TMDB не попадает.
**Статус:** не выполнен

### Контекст

`docs/07_reverse_proxy.md`, код `:proxy` (P2), `data/network/NetworkConfig.kt`,
`data/remote/interceptor/ApiKeyInterceptor.kt`, `di/NetworkModule.kt`,
`README.md`.

### Задача

Переключить клиент на режим `PROXY` (по умолчанию) с сохранением
dev-режима `DIRECT` для работы без сервера.

### Требования (критерии приёмки)

- Режим определяется `local.properties`: `TMDB_PROXY_URL` задан →
  `PROXY` (base URL = прокси, ключ **не** подставляется); не задан →
  `DIRECT` (текущее поведение, ключ из `TMDB_API_KEY`). Решение
  фиксируется в `BuildConfig`/`AppConfig`-объект с логированием режима
  при старте.
- В режиме `PROXY` `ApiKeyInterceptor` не устанавливается; DTO/эндпоинты
  не меняются (прокси совместим по контракту).
- `RateLimitInterceptor` остаётся (клиентский retry на `429` прокси).
- Оффлайн/ошибки прокси классифицируются как раньше (`Network`/`Server`),
  UI-тексты не меняются; новый вариант — прокси недоступен при
  `PROXY`-режиме: тот же `ErrorScreen` (нет отдельного состояния).
- Unit/UI-тесты `:app` — 171+ без изменений проходят; новые тесты:
  `AppConfig` выбирает режим по параметрам (2+ кейса).
- `README.md`: раздел «Reverse-proxy» (запуск `:proxy` локально,
  `TMDB_PROXY_URL` в `local.properties`, деплой по P2), обновление
  раздела «Ключ TMDB» (нужен только для dev-режима `DIRECT`).
- Смоук (ручной, QA): приложение с запущенным локальным `:proxy`
  (напр., на телефоне/в той же сети) проходит сценарий B2–B5 из
  `docs/QA_CHECKLIST.md` **без ключа в `local.properties`**.

## P4. Постепенное усложнение пар

**Результат:** `PairGenerator` работает по профилю сложности игрока:
новичку — известные актёры из свежих высокорейтинговых фильмов, с победами
пары постепенно сложнее (фильмы старше, актёры менее известные); режим
можно выбрать вручную.
**Статус:** не выполнен

### Контекст

`docs/04_algorithms.md` (BFS, Budget, PairGenerator),
`domain/util/PairGenerator.kt` (`PairGenConfig`, `START_ACTOR_POOL`),
`data/remote/dto/TmdbPersonMovieCreditDto.kt`,
`domain/model/GameResult.kt`, `data/local/database/AppDatabase.kt`,
`feature/home/HomeScreen.kt`.

### Задача

Ввести профиль сложности с авто-прогрессией по победам и ручным
выбором режима; генератор учитывает «свежесть» фильмов и известность
актёров.

### Требования (критерии приёмки)

Данные (новые поля):

- `vote_average`/`vote_count` — в `TmdbPersonMovieCreditDto` и
  `TmdbMovieCreditsResponseDto` (уровень фильма); домен: `Movie.rating`,
  `MovieCredit.rating`; сохранение в Room.
- `popularity` уже приходит в DTO — поднять в доменную модель `Actor`
  (`Actor.popularity`, если ещё нет).
- Room: новая версия БД; **паттерн cacheVersion** — инвалидация
  TMDB-кэша bump'ом версии (колонка в кэш-таблицах или drop TMDB-таблиц
  при старте); игровые таблицы (`game_session`, `chain_step`) не трогать.

Домен (профили):

- `DifficultyProfile(mode, minMovieYear, minRating, minActorPopularity,
  preferredMinSteps, preferredMaxSteps)` с именованными пресетами
  (значения — дефолты, тюнятся в одном месте):
  - **EASY**: год ≥ (текущий−15), рейтинг ≥ 7.0, popularity ≥ 40, шаги 2–3;
  - **NORMAL**: год ≥ (текущий−30), рейтинг ≥ 6.0, popularity ≥ 15, шаги 3–4;
  - **HARD**: год ≥ 1980, рейтинг ≥ 5.5, popularity без нижнего лимита,
    шаги 4–6.
- Прогрессия: новая Room-таблица `player_progress`
  (wins, games, bestSteps, avgSteps); `ProgressionPolicy` (auto-режим):
  0–2 победы → EASY, 3–9 → NORMAL, 10+ → HARD; обновление в
  `FinishGameUseCase` при `WIN`.
- `PairGenerator` по профилю:
  - стартовый пул — не хардкод `START_ACTOR_POOL`, а top-N по
    popularity из seed-списка известных актёров (переносится в `domain`),
    отфильтрованных по `minActorPopularity`; в HARD пул расширяется
    актёрами из уже открытых фильмов (неизвестные);
  - кандидаты-цели обязаны иметь хотя бы один фильм, подходящий
    `minMovieYear`/`minRating`.
- Fallback: если пара не найдена в бюджете → релаксация профиля на один
  шаг (снижение minMovieYear, затем minRating; шаги и страна не
  трогать) и повтор; иначе `NoValidPair`.

UI (настройки, часть 1):

- `feature/settings/SettingsScreen` (+ViewModel): секция «Сложность»:
  auto (по умолчанию, показывает текущий тир и число побед) / easy /
  normal / hard; хранение в Room (`player_settings`), применяется
  с новой партии.
- Вход в настройки с Home (иконка); на экране партии — подпись
  «Режим: auto (normal), побед: 5».

Тесты:

- `ProgressionPolicy`: границы 2/3 и 9/10 побед;
- `PairGenerator` на фейковом графе с атрибутами год/рейтинг/popularity:
  EASY выбирает свежие/рейтинговые, HARD — старые/неизвестные; релаксация
  срабатывает; seed-пул заменяет хардкод;
- `player_progress` обновляется после победы (Robolectric Room);
  настройки сохраняются и применяются (ViewModel);
- `detekt`/`lint`/`test` зелёные; README: «Возможности» + примечание,
  что popularity — оценка TMDB, а не факт.

## P5. Страновые ограничения пар

**Результат:** игрок выбирает **произвольные** страны (одну или несколько)
из списка стран TMDB; вся цепочка — актёры и фильмы — остаётся в пределах
выбора.
**Статус:** не выполнен

### Контекст

P4 (профили сложности), `data/remote/dto/TmdbPersonDto.kt`
(сейчас нет `place_of_birth`), `data/remote/dto/TmdbMovieCreditsResponseDto.kt`
(нет `original_language`), `feature/settings/SettingsScreen.kt` (P4),
`domain/util/PairGenerator.kt`, `core/ui/ErrorMapper.kt`.

### Задача

Страновой фильтр (произвольный набор стран) в профиле генерации и в
настройках игрока.

### Требования (критерии приёмки)

Данные (новые поля):

- `place_of_birth` — в `TmdbPersonDto` и cast-DTO; домен: `Actor.birthCountry`
  — нормализованное имя страны («USA», «Russia»); парсер формата
  «City, Region, Country» — `domain/util`, неизвестное/пустое → null.
- `original_language` — в movie-DTO (credits и details); домен:
  `Movie.originalLanguage`.
- Список стран TMDB — эндпоинт `configuration/countries` (уже в
  whitelist прокси, P1/P2); один запрос, долговременный кэш (Room,
  TTL 30 дней).
- Room: bump версии БД по паттерну из P4.

Домен:

- `CountryFilter(selected: List<String>)` — **произвольный** набор стран;
  пустой набор = «Любая» (фильтр выключен). Готовых пресетов нет.
- Фильтр актёров: `birthCountry` ∈ selected (строгое сравнение по
  нормализованному имени страны, без учёта регистра).
- Фильтр фильмов — задокументированное приближение: встроенная таблица
  «страна → языки» для распространённых стран (US/GB/CA/AU/IE→en,
  RU→ru, DE→de, FR→fr, ES→es, IT→it, JP→ja, KR→ko, CN→zh, TR→tr,
  PL→pl, UA→uk и т.п.); фильм допустим, если `original_language` ∈
  объединённым языкам выбранных стран. Для выбранных стран, у которых
  язык не найден, фильм-фильтр **отключается** (актёрский остаётся
  активен) — задокументированное ограничение; точный фильтр фильмов по
  `production_countries` — «дальнейшее развитие» (требует details-запроса
  на фильм и отдельного бюджета).
- Фильтр действует: (а) на стартовый пул и кандидатов-цели;
  (б) на валидацию переходов — фильм вне набора не является валидным
  шагом (цепочка не выходит за выбор).
- Гарантии решаемости для редких стран нет: fallback — сначала релаксация
  P4 (год/рейтинг), страновое ограничение **не** ослабляется; если пар
  нет — отдельный исход `NoPairInCountry` (расширение
  `PairGenerationError`) с текстом «Для выбранной страны мало данных —
  попробуйте ещё раз или выберите другую» (`ErrorMapper`).

UI:

- Настройки, секция «Страна»: searchable-список стран TMDB,
  мультиселект (чипы выбранных), «Любая» (сброс выбора), хранение в
  `player_settings` (список имён).
- Подсказка в настройках: «Для маленьких стран пара подбирается дольше
  или может не найтись».
- Экран партии: подпись активных стран (до 2 + «…»; пустой набор —
  «Любая»); пикеры (фильмы/актёры) показывают только допустимые
  сущности — фильтрует репозиторий (UI не знает о фильтре).

Тесты:

- парсер `place_of_birth` (10+ кейсов: «Moscow, Russia»,
  «Los Angeles, California, USA», «Berlin, Germany», мусор, пусто);
- таблица «страна → языки» (включая кейс «язык не найден»);
- `PairGenerator` на фейковом графе с атрибутами стран: выбор Германии —
  цепочка не проходит через российские/американские фильмы и актёров и
  обратно; две страны — обе разрешены; сущности с null страной в
  ограниченном режиме не выбираются; редкая страна — `NoPairInCountry`
  (а не `NoValidPair`);
- настройки: мультиселект сохраняется и применяется (ViewModel);
- `detekt`/`lint`/`test` зелёные; README обновлён.

## P6. Онлайн-дуэль (1 на 1)

**Результат:** режим «Дуэль»: два игрока получают одинаковую пару и
соревнуются, кто быстрее соберёт цепочку; результат валидируется сервером.
**Статус:** не выполнен

### Контекст

модуль `:proxy` (P3: доступ к TMDB и ключ на сервере), P4 (профили
сложности), P5 (страны), `docs/04_algorithms.md` (валидация цепочки),
`domain/model/ChainStep.kt`, `domain/usecase/StartGameUseCase.kt`,
`feature/home/HomeScreen.kt`.

### Задача

Онлайн-дуэль 1 на 1: одинаковая пара, соревнование по времени,
валидность цепочки проверяет сервер через TMDB.

### Требования (критерии приёмки)

Протокол (`:proxy`, новые эндпоинты; хранилище v1 — SQLite на сервере;
без аккаунтов: игрок = ник + случайный токен):

- `POST /duel/create {name, settings}` → `{duelId (код из 6 символов),
  pair, startAt, myToken}`: создатель генерирует пару локально (обычный
  `StartGameUseCase` с текущими настройками P4/P5) и отправляет её
  серверу; сервер фиксирует пару и `startAt` (время сервера) — гонка
  стартует у обоих в один момент.
- `POST /duel/{id}/join {name}` → `{pair, startAt, myToken, serverTime}`:
  второй игрок получает **ту же пару**; offset `serverTime - localTime`
  используется таймером клиента.
- `POST /duel/{id}/result {chain: List<ChainStep>, totalMs}` →
  `{status: WIN|LOSE|DRAW|DISQUALIFIED, myTimeMs, opponentTimeMs?}`:
  сервер валидирует цепочку — каждый шаг валиден (актёр в cast фильма,
  связность «фильм → следующий актёр»), концы цепочки совпадают с парой;
  валидация только в момент подачи (запросы к TMDB ≤ шагов+1);
  невалидная цепочка — `DISQUALIFIED`. Первая подача побеждает;
  повторная — `409`.
- Таймаут: 15 минут от `startAt` без результата — дуэль закрывается;
  игрок с результатом получает финальный статус, другой — «соперник
  отключился».
- Anti-flood: rate-limit на дуэльных эндпоинтах по токену.
- Реальное время прогресса соперника, аккаунты, матчмейкинг («найти
  любого»), лидерборды — «дальнейшее развитие» (не v1).

Клиент:

- Home: кнопка «Дуэль» (рядом с «Начать игру») → экран с двумя вкладками:
  «Создать дуэль» (генерация пары → показать 6-символьный код, ожидание)
  и «Войти в дуэль» (ввод кода).
- Экран дуэли — тот же игровой экран + баннер: ник соперника, таймер от
  общего `startAt` (по offset); сдача фиксируется на сервере.
- Экран результата дуэли: победа/поражение/ничья, время обоих, своя
  цепочка (если победил), кнопки «Новая дуэль» / «В меню».
- Пара в дуэли — с текущими настройками создателя (сложность, страна);
  соперник видит только пару.
- Дуэль без сети недоступна — понятное сообщение; локальная партия
  остаётся доступной.

Тесты:

- сервер (unit, MockEngine для TMDB): валидация цепочки (валидная /
  разрыв / неверные концы), первая подача побеждает, дубль — `409`,
  таймаут, rate-limit;
- клиент: ViewModel дуэли (создание/код, join, offset таймера, сдача,
  ошибка без сети), Compose UI-тест: создать → код показан → (фейковый
  сервер) → экран дуэли с той же парой;
- `detekt`/`lint`/`test` на корне (оба модуля) зелёные; README: раздел
  «Дуэль» + ограничения (без реального времени и аккаунтов в v1).
